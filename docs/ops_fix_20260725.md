   `EnableOpsLog=true`・`Mult_BTC_FUND/BFXREV/ETH=2.0` を目視確認
5. **プロファイルを保存して起動経路を一本化**（重要・再発防止の本丸）:

   - `claude_startup_xm_v13.ini` の`[StartUp]`のExpertアタッチ先チャート（Symbol/Period指定）を
     **手順3で開いたチャートと同一（BTCUSD・同じ時間足）に修正**する。
     iniとプロファイルが**別のチャートを指していることが二重化の根因**。同一チャートを指せば
     再起動時はプロファイル復元とini適用が同じ1枚に収束する
6. **自動売買ボタンをON**
7. **是正日時（JST・分まで）を記録** → §5のフラグと台帳v2の`--s4-end`に使う

## 2. S-3 + S-4手順2: watchdog（check_and_recover.ps1）の判定修正（運用PC・約20分）

`check_and_recover.ps1`は運用PCローカルのため、**リポジトリ側は関数ライブラリ`ops/watchdog_lib.ps1`を
正とし、本体はそれを呼ぶ形に改修**する。復旧パス（kill→再起動→ポーリング。15/15成功・平均25秒の実績）は
**そのまま残す**。変えるのは判定だけ。

### 統合手順

1. リポジトリを運用PCへ`git pull`
2. まず**ライブラリのテストを運用PCでも実行**して環境差がないことを確認:
   ```
   powershell -NoProfile -ExecutionPolicy Bypass -File ops\test_watchdog_lib.ps1
   ```
   → `RESULT: pass=25 fail=0` であること
3. `check_and_recover.ps1`の冒頭に dot-source を追加:
   ```powershell
   . "<repoパス>\ops\watchdog_lib.ps1"
   ```
4. 端末ごとの設定を定義（パスは運用PCの実パスに置換）:
   ```powershell
   $terminals = @(
     @{ Name='XM';        DataDir='<XM端末データDir>';       ProcessPath='<XM terminal64.exe>';
        EaPattern='MIX_EA';        ExpectedInstances=1; MixlogPrefix='mixlog' },
     @{ Name='OANDA-FX';  DataDir='<OANDA FX端末データDir>';  ProcessPath='<OANDA FX terminal64.exe>';
        EaPattern='MIX_EA_OANDA';  ExpectedInstances=1; MixlogPrefix='mixlog_oa' },
     @{ Name='OANDA-CFD'; DataDir='<OANDA CFD端末データDir>'; ProcessPath='<OANDA CFD terminal64.exe>';
        EaPattern='MIX_EA_OANDA';  ExpectedInstances=1; MixlogPrefix='mixlog_oa' }
   )
   ```
   - `DataDir` = `logs\`と`MQL5\Files\`を含むディレクトリ（ジャーナルが`<DataDir>\logs\yyyyMMdd.log`にあること）
   - `EaPattern`は正規表現。XM側を`'MIX_EA'`にすると`MIX_EA_OANDA`にもマッチしない（`\s`境界があるため安全）
5. 旧`Test-EaLoaded`（`check_and_recover.ps1:47`付近の`Get-LatestSessionText`ベース判定）の呼び出しを
   `Test-EaHealth`に置換（`$t`は`$terminals`のループ変数）:
   ```powershell
   $h = Test-EaHealth -Terminal $t   # -Now は省略（現在時刻）
   switch ($h.Status) {
     'OK'      { }                       # 従来の "OK - untouched" ログ
     'GRACE'   { }                       # 起動直後。ログのみ・次回30分後に再判定
     'SKIP'    { }                       # 00:00-00:15のロールオーバー窓。ログのみ
     'PROBLEM' {
        if ($null -ne $h.InstanceCount -and $h.InstanceCount -gt 1) {
           # S-4: 二重ロードは再起動では直らない(ini/プロファイル不整合が原因)→通知のみ・手動是正
           #      §1完了後は再起動でも1枚に収束するので、その後は自動復旧に含めてもよい
           <既存の通知パス msg.exe 等>
        } else {
           <既存の復旧パス kill→再起動→ポーリング>   # 従来どおり
        }
     }
   }
   ```
6. 判定仕様（`watchdog_lib.ps1`ヘッダにも記載）:
   - **プロセス死は常にPROBLEM**（ログ非依存・ロールオーバー窓でも抑制しない）
   - ジャーナルは**当日+過去14日**を走査し、最終セッション開始マーカー以降のEAロード/削除イベントで判定
     →「日付が変わった直後に当日ログが無い」ケースで誤検知しない（S-3の本体修正）
   - **インスタンス数 > 期待値1 はPROBLEM**（S-4検査。実イベントに基づく陽性証拠なので窓内でも抑制しない）
   - 再起動直後10分は`GRACE`（EA初期化待ち。誤検知防止）
   - ジャーナルに証拠が全くない場合はmixlogの更新鮮度（既定78時間・週末跨ぎ考慮）にフォールバック
   - 00:00-00:15 JSTはログ依存の陰性判定のみ`SKIP`（保険。S-3修正候補(c)の時間帯ガード）

## 7. F-3（PairTrade決済遅延）の確定情報と観察ポイント

開発側でEAコードから確定（[MIX_EA.mq5:421](../experts/MIX_EA.mq5)）:

- 決済判定は**新バー到来時のみ**実行。ただし`OnInit`で全枠`lastBar=0`にリセットされるため、
  **EA再ロード直後の最初のティックで1回だけ即時再評価が走る**（仕様。7/22のOANDA 00:07:03決済 =
  00:06:15再ロード後の初ティック）
- z計算は**確定バーのみ**（shift=1）なので、バー頭評価でも再ロード後評価でも入力データは同一。
  時刻ズレ=執行スリッページであり、シグナル自体の差ではない
- JST 00:00はOANDAサーバーのNYクローズ・ロールオーバー帯と重なり、ティックが数分枯渇しうる。
  **S-3修正後もPairTrade決済だけ数分ズレが残る可能性がある**が、実害は執行時刻のみ
  → 台帳v2のTIMEDIFF除外が吸収する
- **観察:** S-3修正後の最初のPairTrade決済で、XMとOANDAが同一分なら誤再起動起因と確定（クローズ）。
  依然ズレるならロールオーバー帯のティック枯渇（仕様・対応不要）として週次に記録
