## 2. 原因と修正

MT5 の `[Tester]` セクションの `Leverage` は **`1:25` 形式**で書かなければならない。
`25` と書くと解釈されず、既定値が使われる。

```python
# mt5bt/runner.py（修正前）
"Leverage": str(cfg.leverage),          # -> "25"  …… 無視され 1:100 になる
# （修正後）
"Leverage": f"1:{int(cfg.leverage)}",   # -> "1:25"
```

**黙って落ちるのが最悪なので、検証も入れた。** `MT5Runner.verify_leverage()` が
毎 run ジャーナルを読み、`config` の値と突き合わせて不一致なら警告を出す。

短い検証 run（2017.01〜2017.03・PB USDJPY と RSI USDJPY のみ）で
`レバレッジ確認: 1:25` を確認済み。

資金経路が変わり、内訳も張り付きも変わる。**再測定が要る。**

## 4. 「約10倍過大」の訂正 — 内訳は倍率4倍と含み益の複合

`margin_feasibility.py` は **LEVERAGE=25 で**証拠金を積んで、T036 の最悪点
（2021-02-12・決済ベースequity 445,091円）で **988.3%** を出していた。

実機は 1:100 だったので、同じ建玉の必要証拠金は **1/4 = 247%** である。
それでも100%を超えているのに拒否が出ていないので、**残りは含み損益**で説明するしかない。

| 要因 | 寄与 |
|---|---|
| レバレッジが4倍ゆるかった | 988% → **247%** |
| equity に含み益が入っていなかった | 247% → **実際は80%未満** |

**「決済ベースequityは常に下振れする／再構成は約10倍過大」という第4報の書き方は撤回する。**
倍率の誤りが主因の一つであり、含み益だけで10倍を説明することはできない。

Codex の指摘で、最悪点の建玉の中身も確認した——
**PB GBPJPY は数か月保有ではなく約3日**（2021-02-09建て）。
含み益が大きかったのは **Carry AUDJPY（2020-06-02建て・2.89ロット）**のほうである。
「Carry と PB がどちらも数か月級で持つ」という第4報の説明は、**PB については誤り**。

> [!note] 「cap が一度も発動していない」も、厳密には未証明
> `MarginCapLot()` は `OrderCalcMargin` 失敗時や価格取得失敗時に**制限せず元のロットを返す**。
> また cap で削っても前後がともに50ロット以上なら、後段の銘柄上限で同じ50に落ちる。
> 確実に言えるのは「**最終約定への影響がゼロだった**」まで。
> 発動回数を数えるにはEAにカウンタが要る。

## 5. 窓別再測定（`windows_stage3.py`）にも集計の誤りがある

Codex の指摘。窓は「**建てた時刻が窓内**」で選び、決済は窓外でも加算する一方、
月利の分母は「**決済のあった月**」だけを数えている。結果、24か月窓のはずが——

| 表示窓 | 月利 | 実際に数えた決済月数 | 最後の決済月 |
|---|---:|---:|---|
| 2016-11〜2018-11 | 22.25% | 24 | 2018-10 |
| 2017-11〜2019-11 | 7.04% | **26** | **2019-12** |
| 2018-11〜2020-11 | 5.29% | **26** | **2021-06** |
| 2019-11〜2021-11 | 4.05% | **20** | 2021-06 |

**同じ長さの運用を比べていない。** 「中央値 6.17%」はこの混ざった集計の上の値である。
加えて12か月刻みの24か月窓は重なっており、**4本は独立標本ではない**。

さらに「上限50で切られているから保守側に下振れする」という私の記述も**誤り**。
ロットを小さく見積もれば利益も損失も小さくなるので、**誤差の向きは不定**である。

→ この軸は `ml/fxwin1/`（各窓を独立した MT5 run として実測）で置き換える。
再構成に頼らなければ、この種の集計の誤りは最初から起きない。
**ただし fxwin1 も 1:25 で回さなければ意味が無いので、`ml/fxlev25/` の後に回す。**
