## 依頼1: 査読

### (A) Carry の配賦修正

結論として、今回の事実認定は正しいです。`entry=0` を IN、`entry=1` を OUT として、OUT の `magic=0` を同一 `position_id` の IN 時 magic に戻す処理は、今回のログ形式では妥当です。

実データも確認しました。

- `fxqual1` の44ログで `entry` は **0 と 1 のみ**。
- `magic=0` は **107件すべて entry=1**。
- 各ファイル内で、同一 `position_id` に複数の IN magic はありません。
- `fxmargin3` でも同じ構造で、magic=0 は OUT 側25件のみです。

よって、今回の「テスト終了時の強制決済だけ magic=0」というケースには、[`reattribute.py`](/C:/Users/f/source/repos/mt5_backtester/ml/fxqual1/reattribute.py) と [`measure.py`](/C:/Users/f/source/repos/mt5_backtester/ml/fxmargin3/measure.py) の修正は合っています。Carry の OOS `+26,061円`、IS `+76,743円` への訂正、および Q019–Q021 の差分を Carry に全量戻す読みも正当です。「他枠への副作用」は撤回すべきです。

ただし、この実装は一般的な deal 帳簿としてはまだ限定的です。将来壊れるケースは次です。

- **netting 口座で反対売買して反転する場合**  
  MT5 の `DEAL_ENTRY_INOUT=2` は一つの deal が決済と新規建てを兼ねます。現在は `entry != "0"` をすべて OUT とみなし、その deal の magic に全損益を置きます。元建玉の magic と反転注文の magic が違えば、決済部分が誤配賦になります。
- **同一 symbol を複数 magic が共有する netting 口座**  
  PB/RSI/SCA が USDJPY を共有しています。hedging 口座なら問題ありませんが、netting では position_id と magic が strategy の一対一キーになりません。そもそも EA の戦略分離自体が崩れます。
- **close-by (`DEAL_ENTRY_OUT_BY=3`)**  
  現コードは OUT 扱いになるので、通常の部分決済なら問題ありません。ただし close-by には相手 position の情報も必要になり得るため、片方の IN magic だけで全損益を決めるのは不十分です。
- **部分決済**  
  今回のように position_id が一意な hedging 建玉なら正しく、複数 OUT を同じ owner に合算できるので問題ありません。
- **同一 position_id に複数 IN が発生する構造**  
  現在は辞書内包表記の最後の magic が勝ちます。将来 `INOUT` や増し玉の扱いを変えるなら危険です。

改善するなら、`entry` を文字列の `0/1` に依存させず、`DEAL_ENTRY_IN/OUT/INOUT/OUT_BY` 相当を明示し、次を検査して異常時は停止するのが安全です。

- `entry` が 0/1 以外なら警告・未配賦扱い。
- 一つの position_id に複数 IN magic があれば例外。
- `magic=0` の OUT に owner がなければ例外。
- `book_net - (sum_sleeves + orphan)` を毎 run 出力し、1円超なら失敗。

また、Carry IS `+76,743円` のうち `+52,551円` が窓末評価である点は重要です。これは Carry の恒常的エッジの証拠ではなく、「その日に閉じたらそうだった」という窓端効果です。Carry の品質判定には、窓末強制決済を含む net より、実決済分と未実現分を分けた報告を必須にすべきです。

### (B) RSI 内訳

読みは概ね正しいですが、組合せ別損益をそのまま「この群を除けば増益」とは読めません。ゲートを入れると、

- 落としたシグナルのフラグが残るか、
- その後の別組合せの発火が変わるか、
- 同方向保有・ドテンとの衝突が変わるか、

が変わるため、取引列は経路依存になります。

それでも優先順位は明瞭です。

- **EURUSD:** RB のみが唯一の強い候補。B単独・R単独は明確に悪い。
- **USDJPY:** D を含む群が候補。B単独、R単独、RB は残す根拠が弱い。
- **GBPUSD:** B単独は強いが、RB も正であるため、B単独化は「改善」ではなく取引削減の賭けです。優先度は低いです。

ご提案の `RsiMechMask_UJ/_EU/_GU` は、すでに [`MIX_EA_SIMVERIFY.mq5`](/C:/Users/f/source/repos/mt5_backtester/experts/MIX_EA_SIMVERIFY.mq5) に実装済みで、`eb/es` に正しく掛かっています。組合せコードと bit の定義も正しいです。

フラグは**ゲートで落とした足では消費しない**のが正解です。消費すると「RB合流だけ待つ」ではなく、先に来た単独 B/R で機会を破棄する別戦略になります。これは現在の実装とも一致しています。

ただし、無期限に残すのも危険です。機構ゲート試験では、最初は「残す」だけにして因果を切り分け、採用候補だけ `RsiBBFlagMaxBars` / `RsiRSIFlagMaxBars` を併用して寿命を別試験にすべきです。mask とフラグ寿命を同時に動かすべきではありません。

### (C) Pair の z

正しい読みです。`|z| >= stopZ` で新規建てするのは、注文直後から停止条件の外側にいる設計不整合です。6/30脚、`-2,716円` 対 `+4,712円` なら、`PairSkipAtStop=true` は第2ラウンドで最も筋のよい案です。

ただし30脚しかなく、しかも両脚集計なので、金額の符号だけで採用はできません。T001 の OOS/IS 両方が揃うまで、次の Pair 変更多発は避けるべきです。

## 依頼3: 6%への見込み

**枠の質改善だけで 0.39%/月から6%/月を埋める見込みは、ありません。** 率直に言えば低いどころか、統計的に期待すべきではありません。

今回の有望2案でさえ、現行固定サイジングでは概ね `+0.01〜0.03pt/月` 級です。仮に全案が都合よく同方向に当たっても、現実的には `+0.1pt/月` 前後で、必要な `+5.61pt/月` には桁が二つ足りません。

さらに、Carry のIS利益は窓末含み益に大きく依存し、RSI機構別・Pairの30脚もサンプルが小さいです。ここで「良いタグだけ残す」を繰り返すほど、IS/OOS両窓に対する選別バイアスが強くなります。

未消化の筋があるとすれば、既存9枠の微修正ではなく次です。

- **新しい、独立したエッジの獲得**。既存機構の横展開は多くが否定されているため、同型パラメータ探索ではなく、異なる保有期間・情報源・市場構造が必要です。
- **目標と制約の再定義**。実行可能最良の2.18%/月・DD30.6%から6%を狙うなら、許容DD、レバレッジ、運用資本、または「OOS幾何月利6%」のいずれかを変えない限り整合しません。
- **フォワード実績の蓄積**。特にCarryは実現損益・未実現損益・スワップを分離し、窓端なしのrolling評価に変えるべきです。

第3ラウンドは、収益目標を達成する手段ではなく、RSI/PB/SCAの残った不整合を低コストで潰すラウンド、と位置付けるのが正確です。
