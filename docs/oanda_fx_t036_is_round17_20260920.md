## 0. なぜこのラウンドをやるのか

主題は引き続き **枠ごと（戦略ごと）の質の改善**である。ただし第16報で
Codex が「B は該当なし。未測定軸として再提案できるものはありません」と答え、
**全複利ブックの上での枠の質は13ラウンド・約100案・224run で打ち止め**になっている。

そこで本ラウンドは、**同じ枠の質の軸を「別のブックの上」で測り直す**。理由は2つ。

1. 🔴 [OANDA 端末 cap 掃引](oanda_fx_terminal_cap_sweep_20260919.md) で見つかった
   **T036系 cap50 は OOS 5.537%/月**と、全複利ブックの最良（OOS 3.849%）より 1.7pt 高い。
   にもかかわらず **IS 窓を一度も測っていない**ので採用候補にできていない。
   **「実行可能な最良」が確定していない。**
2. 第1〜13ラウンドの約100案は**すべて全複利ブック（9枠・risk% 一律 0.5%）の上**で測られた。
   T036系は **RSI 3枠に実効3%/取引**を集中させる別構成なので、
   **同じ出口の軸でも効き幅が別物になりうる**（第22報「複利の増幅は 12〜121倍」）。

## 5. 🔴 走らせる前に踏んだ地雷 — OANDA 端末の EA が古かった

| 場所 | 版 | サイズ |
|---|---|---|
| OANDA BT1 の `MQL5/Experts` | **2026-09-18 00:13** | 149,077 バイト |
| リポジトリ `experts/`（＝XM 端末と同一） | 2026-09-19 20:08 | 196,104 バイト |

**古い版は第12〜13ラウンドで足した `RsiTpMask_*` / `ScaRR_*` / `ScaOvsATR_*` / `ScaBE*` を持っていない。**
MT5 は知らない input を**黙って無視する**ので、そのまま走らせれば
`O020`/`O021`/`O022`/`O023` が `O000` と完全同値になり、
**「効かなかった」という結論に化けていた**（第16報で実際に踏んだ形）。

→ `chain.ps1` が **OANDA 側の `MetaEditor64.exe` で再コンパイルしてから**走らせる。
旧 `.ex5` は `MIX_EA_SIMVERIFY.20260918.ex5.bak` に退避する。
**XM 端末（`BAC624...`）には一切触らない**ので、並行セッションとバイナリを取り合わない。

### 回帰 `O000` の読み方（ここを曖昧にしない）

追加 input はすべて既定が no-op であることをソースで確認した
（`RsiTpMask_*=0` / `ScaRR_*=0.0` / `ScaFilMask=0` / `LotFloorMask=0` …）。
**`TagDealTriggers` と `PbDiagCounters` だけは `true` にしている**が、
前者は**注文コメント文字列**を変えるだけ（`RSI` → `RSI:RB`）、
後者は**カウンタと CSV 出力**だけで、どちらもロット・価格・SL/TP に触れないことを実装で確認した。

それでも diff には `LotRisk()` まわりの書き換えが含まれる。だから:

> **`O000` が一致しなかった場合、原因の候補は2つあり、この1本では切り分けられない。**
> **(a) EA の版が変わって挙動が変わった／(b) fxoanda3 の数字がそもそも再現しない。**
> **どちらであっても「fxoanda3 の数字と本ラウンドの数字を並べてはいけない」ことは確定する。**
> その場合は**止めずに走り切り、fxoanda4 内で閉じた比較だけ**を行う（`measure.py` の `check()` がそう実装してある）。

## 6. Codex が出した「まだ測っていない軸」（本ラウンドで消化しないもの）

Codex は T036 の上で再評価する価値がある軸を7件（A01〜A07）挙げたが、
**A01(UJ TP)・A03(GU TP) 以外はすべて自ら「見込み低」と書いている**。本ラウンドでは A01/A03 のみ測る。
残りは `O001` の結果を見てから判断する（T036 が IS で崩れるなら、そもそも掘る土俵ではない）。

**EA 改修が要る軸は2件。どちらも本ラウンドでは実装しない**（並行セッションと「EA を触らない」で合意済み）。

| ID | 中身 | Codex の見込み |
|---|---|---|
| A08 | 親 SCA のリバーサル boost を `ScaBoostMult_UJ/GJ` として input 化（現状は 6.0/2.0 のハードコード） | 中 |
| **A09** | **維持率ガード**: `MinMarginLevelPct` / `ResumeMarginLevelPct` で新規を止める（第1段）、`MarginEmergencyPct` / `MarginReduceFraction` で部分決済（第2段） | **高（利益ではなく実行可能性）** |

> [!important] **A09 は「`MarginCapPct` では OANDA の 100% ロスカットを守れない」という構造的な穴への答えである。**
> `MarginCapPct` は**発注時**に `使用証拠金 ≦ equity × cap%` を掛けるだけで、**建てた後の維持率を保証しない**。
> cap70 は建て直後 143% で、**逆行 30% 弱で切られる**。Codex の初期値案は
> 新規停止 180% / 再開 220% / 緊急削減 135%。**第18ラウンドの筆頭候補。**
