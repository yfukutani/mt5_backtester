## 0. なぜこのラウンドをやるのか

主題は引き続き **枠ごと（戦略ごと）の質の改善**である。ただし第16報で
Codex が「B は該当なし。未測定軸として再提案できるものはありません」と答え、
**全複利ブックの上での枠の質は13ラウンド・約100案・224run で打ち止め**になっている。

そこで本ラウンドは、**同じ枠の質の軸を「別のブックの上」で測り直す**。理由は2つ。

1. 🔴 [OANDA 端末 cap 掃引](oanda_fx_terminal_cap_sweep_20260919.md) で見つかった
   **T036系 cap50 は OOS 5.537%/月**と、全複利ブックの最良（OOS 3.849%）より 1.7pt 高い。
   にもかかわらず **IS 窓を一度も測っていない**ので採用候補にできていない。
   **「実行可能な最良」が確定していない。**
2. 第1〜13ラウンドの約100案は**すべて全複利ブック（9枠・risk% 一律 0.5%）の上**で測られた。
   T036系は **RSI 3枠に実効3%/取引**を集中させる別構成なので、
   **同じ出口の軸でも効き幅が別物になりうる**（第22報「複利の増幅は 12〜121倍」）。

## 8. 🔴 訂正 — 「実行可能」と書いてきたものは実行可能性を測っていなかった（2026-09-20 追記）

並行セッションの指摘で、**本書 §7 を含め、これまでの「実行可能な最良」という言い方が
不正確だった**ことが分かった。第23報以降ずっと引きずっていた誤りである。

### 何が間違っていたか

1. `MarginCapPct` は**発注の瞬間**に `使用証拠金 ≦ equity × cap%` を掛けるだけで、
   **建玉後の維持率を保証しない。**
2. **OANDA のロスカットは維持率 100%。XM は 20%。**
   cap90 の建て直後は維持率 ≈111% ＝ **11% の逆行で切られる。**
3. そして **全複利ブックの run はすべて XM 端末で走っている。**
   **MT5 のテスターは端末の口座設定を使う**ので、
   **モデル化されていたのは XM の 20% であって OANDA の 100% ではない。**

> **つまり「元本割れなし・完走した」は、
> 「XM の 20% に当たらなかった」という意味しか持っていなかった。**

| これまでの書き方 | 正しい書き方 |
|---|---|
| 「倍率2・cap90 は実行可能」 | **「発注時の証拠金制約は満たす。建玉後の維持率は未検証」** |
| 「確認済みの実行可能な最良 OOS 3.849%」 | **「発注制約を満たす最良。OANDA で生存するかは未検証」** |

**「危険である」とも書かない。** DD の谷と使用証拠金の山が同時に来たかが分からないので、
正確には **「危険かどうかが測れていない」**である。
**測れていないものを実行可能と書いたことが誤りだった。**

なお **この事実はプロジェクトが 2026-09-17 に既に記録していた**
（[oanda_stopout_level_20260917.md](oanda_stopout_level_20260917.md)・
[ALL_EA_performance.md](ALL_EA_performance.md) に「cap90 の建て直後 ≈111% → 11% の逆行で切られる」と明記）。
**索引にある結論を読まずに上書きしていた形である。**

### 既存のログでは測れなかった

- `*_cap.csv` の `event` 行は**発注時**の equity と使用証拠金しか持たず、
  しかも**発注時は cap の定義上どうしても `100/cap`% 以上**になる → **最小維持率を復元できない**
- `EquityLogFile` は名前に反して**実体が約定ログ**で、equity/証拠金の時系列ではない

### 入れた計装（`experts/MIX_EA_SIMVERIFY.mq5`・0 errors でコンパイル確認済み）

`TrackMarginLevel()` を `OnTick` の先頭（`MasterEnable` の直後）で呼ぶ。
`ACCOUNT_MARGIN > 0` のときだけ `ACCOUNT_MARGIN_LEVEL` を読み、
**最小値・その時刻・そのときの equity と使用証拠金**を保持する。
併せて **維持率が 300/200/150/100% を割っていたティック数**も数える（危険域の滞在時間）。
出力は `CapLogFile` に2行（`margin_level_min` / `margin_level_hist`）。
**`CapLogFile=""` なら1バイトも出ない。読むだけで売買には触れない。**
集計は `ml/fxoanda4/margin_level.py`。

> [!important] ⚠️ **ガードより先に計装を入れた**（並行セッションの指摘。これが肝だった）。
> `MinMarginLevelPct` のようなガードを先に入れると、**入れた時点で最小維持率が閾値で切り上がり、
> 「元の構成がどれだけ危なかったか」が永久に分からなくなる。**
> Codex の A09（ガード）は、**実測が出てから閾値を決める。**

### この訂正が本ラウンドに与える影響

🟢 **本ラウンドは OANDA 端末で走るので、100% のロスカットが実際にモデル化されている。**
XM 側の run と違い、**生存可否を直接測れる。** `O011`（全複利 倍率2・cap90 を OANDA で）は
まさにこれを測る run である。

💡 **維持率そのものは端末のロスカット水準に依存しない量**なので、
**XM 端末で測り直した run でも「100% を割ったか・いつ割ったか」は判定できる。**

> [!warning] ⚠️ **ただし「XM で測れば OANDA の生存可否が分かる」は半分しか正しくない**（並行セッションの訂正）。
>
> | 問い | XM の run で答えられるか |
> |---|---|
> | OANDA なら切られたか・いつか | ✅ **答えられる** |
> | OANDA での月利・DD はいくらか | ❌ **答えられない** |
>
> OANDA なら時刻 T で強制決済されるので、**T 以降の経路が別物になる。**
> XM の run は切られずに続いているため、**T 以降の損益・DD・月利はすべて反実仮想として無効**である。
> 実務的には **「割った構成は、成績を論じる前に候補から落ちる」**という使い方になる。
> **成績を知りたければ、OANDA 端末で（あるいはガードを入れて）測り直すしかない。**

### 🔴 計装そのものにも同じ型の穴があり、出す前に塞いだ

並行セッションの指摘。`TrackMarginLevel()` は `used<=0` / `ml<=0` で**黙って return** するので、
テスターで `ACCOUNT_MARGIN_LEVEL` が取れなければ
**`g_mlMin` も `g_mlLt100` も 0 のまま**になる。
そのまま出すと **「維持率 100% 割れは 0回＝安全」と読めてしまう。実際は「測れていない」。**

**これは本日4回繰り返した型そのもの**（量の名前を、満たしていない性質の含意つきで使う）なので、
**`g_mlSamples==0` のときは数値ではなく `NOT_MEASURED` を書き出す**ようにした。
`margin_level.py` 側も `NOT_MEASURED` を「安全」と数えずに別枠で報告する。

⚠️ `O000` の回帰にはこの計装ぶんの EA 差も乗る。**「触れないはず」で済ませず `O000` の一致で確かめる。**

### 副作用（申し送り済み）

リポジトリの `.mq5` と **XM 端末にデプロイ済みの `.mq5` が食い違った。**
`fxqual16` は DEPLOY_CHECK も再コンパイルも持たないので影響しないが、
**`sameAsRepo` チェックを持つ次の XM チェーンは `CHAIN_ABORT` する。**
次に XM 側を走らせるときは **XM 端末で再コンパイルすること**（計装も同時に載る）。
