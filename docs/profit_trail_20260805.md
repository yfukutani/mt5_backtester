# 利益トレール（Profit Trail）— 実装と効果測定（2026-08-05）

**ユーザー要望:** 「利益が出ているタイミングで利益を確保する手法。含み益が口座残高の0.5%に達したらSLを
口座残高の0.1%の利益を確保する位置に置き、その後は利益が0.5%増えるごとにSLも増加分だけ上げる。
設定でON/OFFできるようにする。」

**実装状況: 完了（MIX_EA v1.5 / MIX_EA_OANDA v1.2・既定OFF）。**
**測定結果: 指定パラメータ（0.5%/0.1%）でONにすると純利益がIS −22.0万円 / OOS −16.9万円。既定OFFを推奨。**

---

## 1. 仕様と入力

| 入力 | 既定 | 内容 |
|---|---|---|
| `UseProfitTrail` | **false** | ON/OFFスイッチ |
| `ProfitTrail_Step` | 0.5 | 発動・引き上げの刻み（口座残高に対する%） |
| `ProfitTrail_Lock` | 0.1 | 初回発動時に確保する利益（口座残高に対する%） |

含み益が「残高 × Step%」に達するごとに段階nを1つ上げ、第n段では
**「残高 × (Lock% + (n−1)×Step%)」の利益を確保する価格**へSLを移動する（追従幅は Step−Lock で一定）。

**残高10万円・既定値での動作:**

| 含み益 | SLが確保する利益 | 追従幅 |
|---|---|---|
| +500円（0.5%） | +100円（0.1%） | 0.4% |
| +1,000円（1.0%） | +600円（0.6%） | 0.4% |
| +1,500円（1.5%） | +1,100円（1.1%） | 0.4% |

**実装上の判断:**
- **毎ティック評価**（既存のVBOトレーリングはバー確定時のみ）。利益のピークを取り逃さないため
- **SLは改善方向にのみ移動**し、現値・ストップレベルを跨ぐ位置には置かない（約定拒否/即決済の回避）
- **判定はスワップ込みの実含み益**。暗号枠のようにスワップ負担が大きい枠では発動が遅くなる保守側の挙動
- **対象はEAが建てた全ポジション**。本来SLを持たない **PairTrade / Carry にもSLが付く**点に注意
- 発動時に運用ログへ `PTRAIL` 行（段階数・含み益・確保額・新SL・現値・数量）を出力。フォワードで検証可能

## 2. 実装中に見つけた重要なバグ（修正済み・他機能への教訓）

初回測定でGOLD・暗号のON/OFF差が**完全にゼロ**（純利益・PF・DD・勝率・取引数すべて同一、`PTRAIL`行も0件）
だったため調査したところ、`SYMBOL_TRADE_TICK_VALUE` が**口座通貨で返らない**ことが判明した。

| 銘柄 | tick_value | 実際の単位 |
|---|---|---|
| USDJPY / GBPJPY | 100.0 | **JPY**（＝口座通貨・正しい） |
| GOLD | 1.0 | **USD**（1USD/lot・未換算） |
| ETHUSD / BTCUSD | 0.01 | **USD**（同上） |

MQL5仕様上この値は「預金通貨」で返るはずだが、XMのUSD建て銘柄では建値通貨のまま返る。
その結果「確保金額→値幅」の換算がドル円レート分（約164倍）過大になり、SLが現在値のはるか先に置かれて
毎回スキップされていた。**JPY建てペアだけで発動する非対称な状態**になっていた。

**修正:** 銘柄仕様に依存せず、**ポジション自身の損益から換算**する:

```
値幅あたりの金額 = POSITION_PROFIT ÷ (現在値 − 建値)
SL距離           = 確保したい金額 ÷ 値幅あたりの金額
```

端末自身の損益計算を使うため通貨・契約サイズ・ブローカー差に依存しない。

> **他機能への教訓:** ロット計算（`CalcLot`）など `SYMBOL_TRADE_TICK_VALUE` を使う既存コードは、
> **JPY建て銘柄でしか検証されていない可能性がある**。USD建て銘柄（GOLD/暗号）で
> risk%サイジングを使う場合は同じ罠に注意すること（現状GOLD/暗号は固定ロットのため実害なし）。

### なぜこうなるか

**勝率は大きく上がる**（GOLD 53.3→61.3% / 暗号 50.8→69.0%）が、**利益は大きく減る**。
これはv2.7（BE）・v2.8（トレーリング）で10年検証したときと同じ signature である。

根本原因は**スケールの不一致**。0.5%/0.1%という刻みは、これらの戦略の利益スケールに対して小さすぎる:

- PB GOLDは**SL幅だけで基準資金の11.4%**（A-1で実測）。0.1〜0.6%を確保する位置にSLを置くのは、
  戦略の尺度では「建値のごく近傍で切る」ことに等しい
- GOLD/暗号はトレンド追随で、少数の大きな勝ちが利益の大半を作る。その勝ちを序盤で刈り取ってしまう
- 取引数が増えている（GOLD 304→310、暗号 63→113）のは、早期決済で再エントリー機会が生まれるため。
  だが1件あたりの利益が縮み、トータルでは負ける

### 刻みを広げた場合（感度）

| ブック | S03（0.3/0.1） | **S10（1.0/0.2）** |
|---|---|---|
| FX IS / OOS | −8.3% / −12.5% | −6.5% / ±0% |
| GOLD IS / OOS | −55.3% / −67.4% | **−0.1% / +1.6%** |
| CRYPTO IS / OOS | −42.3% / −91.7% | −28.8% / −111.2% |

刻みを広げるほど害は小さくなり、**S10（1.0%/0.2%）ではGOLDはほぼ中立**になる。
ただし暗号は依然として大きくマイナスで、FXも改善しない。**どの設定でも全ブックでプラスにはならない。**

## 5. 推奨

1. **既定OFFのまま運用する**ことを推奨する。指定パラメータでは純利益が20〜45%失われる
2. それでも有効化したい場合の選択肢:
   - **暗号3枠は必ず除外**（最も害が大きい・OOSで−86.5%）
   - 刻みを**1.0%以上**にする（GOLDはほぼ中立になる）
   - まずは**フォワードで`PTRAIL`ログだけ観察**する運用（ONにしても発動記録が残るので、
     実際にどの枠でどれだけ発動するかを実弾で確認してから判断できる）
3. 枠ごとにON/OFFを切り替えたい場合は入力を追加できる（未実装・要望があれば対応）

> **注意:** この機能はEAが建てた全ポジションに作用するため、**PairTrade と Carry にもSLが付く**。
> 特にCarryは「SLを置かない」ことが設計思想（DDは決済エンジニアリングでは削れないと検証済み・
> `docs/carry.md`）なので、ONにすると設計から外れる。
