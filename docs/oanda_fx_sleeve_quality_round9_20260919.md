## 1. 事前査読で実装バグが1件見つかった（測る前に直した）

当初案は `armed` の set と同じ行で齢を0に戻していた:

```cpp
if(up && lp<=fastema && qb) { S[i].armedBuy=true; S[i].armedBuyAge=0; }   // ← 当初案
```

> [!warning] **`lp<=fastema` が3バー続けば、齢は3回リセットされる。**
> これで測れるのは「armed されてから N バー」ではなく
> **「最後に押し目を付けてから N バー」**という**別の軸**である。
> しかも**第5ラウンドの「ずれる」問題を PB 側に持ち込む**——
> 期限切れになっても、押し目条件が続いていれば次の足で再 arm されるので、
> **入口が消えるのではなく後ろへずれるだけ**になる。

直した形は**齢の起点を押し目条件の立ち上がりに限定**し、
**`armed` の set/clear の5行は1文字も触らない**:

```cpp
// 既存の set/clear 5行はそのまま（無改変）
if(S[i].armMaxBars>0){                       // ← 0 ならブロックごと実行されない
   bool pbNowB=(up && lp<=fastema && qb);
   if(!up)                          S[i].armAgeB=-1;   // トレンドが壊れたらエピソード終了
   else if(pbNowB && !S[i].pbPrevB) S[i].armAgeB=0;    // 立ち上がりでだけリセット
   else if(S[i].armAgeB>=0)         S[i].armAgeB++;
   S[i].pbPrevB=pbNowB;
   if(S[i].armedBuy && (S[i].armAgeB<0 || S[i].armAgeB>S[i].armMaxBars)) S[i].armedBuy=false;
}
```

**set 側を立ち上がりのみにしなかった理由**: 発注時に `armedBuy=false` が入るので、
立ち上がりのみにすると**発注後に押し目が続いても再 arm されず、`amb=0` でも挙動が変わる。**
齢だけを立ち上がり起点にすれば、**`armMaxBars=0` での同値性はコード上自明**になる。

Pair 側も査読で2点直した:

| 指摘 | 直した形 |
|---|---|
| `PairRequireZTurning=false` でも `zPrev` を書くと既定値に副作用が出る | **false のときは1バイトも書かない** |
| `sd<=0` や `CopyClose` 失敗で z を作れなかったバーの後、古い z と比べて誤判定する | その経路で **`zPrevValid=false` に戻す** |

### 本番移植時に必要なこと（今回はやらない）

`armed` は GlobalVariable に永続化されている（v1.4・EA 1359行）が、**齢は永続化しない。**
ライブ再起動後は齢が −1 になるので、`armMaxBars>0` なら**復元された armed は落ちる。**
「古い arm を使わない」という趣旨には沿うが、本番に載せるなら
`StSnap`/`StSave`/`StRestore` に「arm されたバー時刻」を足して復元時に換算する必要がある。
**テスター／最適化では永続化自体が無効なので、今回の実測には一切影響しない。**

## 3. 事前の予想（**測る前に書く**）

> [!warning] **両方とも期待していない。第5ラウンドの「ずれる」問題が、バー単位で当てはまる。**
>
> 第5ラウンドで、SCA の時間帯ゲートは「止めた発注が消える」のではなく
> **「後ろの足へずれる」**ことが分かり、切り直しの予測（+13,093）が実測（−6,817）と
> **符号ごと逆**になった。**判定条件は「そのゲートが日内で解除されるか」**だった。
>
> - **PB**: armed が期限切れになっても、押し目条件が**一度消えて再成立すれば新しい arm になる。**
>   トレンドが続いていれば押し目は何度も来るので、**入口が消えるのではなく後ろへずれる。**
> - **Pair**: 今日 turning しなくても、`|z|>=entryZ` が続いていれば**明日 turning した足で入る。**
>   一気に閾値内へ戻った取引だけが消える。
>
> つまり**どちらも「取引を減らす」より「取引をずらす」効果のほうが大きい**と予想する。

### 効き幅の見積もり

| 軸 | 当方 | Codex |
|---|---|---|
| PB USDJPY の armed 寿命 | 月利 ±0.02pt | **−0.02〜+0.01pt** |
| PB GBPJPY の armed 寿命 | 月利 ±0.01pt | **−0.01〜+0.01pt** |
| Pair の Z 転換 | 月利 ±0.01pt | **−0.03〜+0.01pt** |

**両者とも「最頻の結果はゼロ近傍か悪化」で一致している。**

### 採否の基準（**先に書く**）

1. **勾配（1/2/3/5/8）が台地か単調でなければ棄却する。** PB USDJPY の OOS は **8 deal ＝ 4往復**
   しかない。`ml/fxqual6` の slope が「1.30〜1.50 の5点が両窓プラス」＝台地だったので
   採用候補になったのと**同じ基準**を当てないと、採用根拠にならない。
2. **正の一点が出ても採らない。** 第16報の V007（OOS の内訳だけで機構を選んで IS を壊した）と
   第7ラウンドの Z007（結果を見てから枠を選んだ）で、同じ失敗を2回している。
3. Pair は OOS 30脚 / IS 56脚しかない。`ml/fxqual2` の T001〜T007 が全部ほぼゼロだった。
   **±0.01pt 以内ならノイズとして扱う。**

## 5. 運用上の事故（記録）

**09:10 頃、`fxqual8` の走行中にリポジトリの `MIX_EA_SIMVERIFY.mq5` を約1分間パッチしてしまった。**

複製に空撃ちするつもりで `sed` でパッチスクリプト内の対象パスを書き換えたが、
**Windows パスのバックスラッシュで `sed` の式が壊れて失敗**した。
`sed` の失敗を確認せずに出力を実行したため、**対象が元のまま＝リポジトリ本体**に当たった。

**実害は無かった**（`git checkout` で復旧・リポジトリと配備先のハッシュ一致・
`.ex5` の mtime 不変・`watchdog8.log` は START の1行のみで再起動ゼロ・
`measure.log` に欠落なし）。**`chain.ps1` が死ななかったので watchdog が起きなかっただけ**である。
窓は約1分、watchdog のポーリングは3分間隔だった。

再発防止として `patch_ea.py` に対象パスの引数を足し、
**複製への空撃ちは引数で明示的に指定する**形にした。パス書き換えの `sed` は使わない。

その後、正しく複製へ空撃ちして13箇所すべてが一意に一致することを確認し、
**複製を `MIX_EA_ARM9TEST.mq5` という別名で MetaEditor にかけて
`Result: 0 errors, 0 warnings` を取った**（配備中の `.ex5` の mtime は不変）。
