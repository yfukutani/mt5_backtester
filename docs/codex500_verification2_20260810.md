## コード監査

### Family 2: 単体EA / MIXシグナル同値性

- 現行本番値について、PB・RSI・SCAの主要シグナル式、確定足参照、新バーゲート、Magic単位のポジション判定は単体とMIXで対応している。今回、新規dealログを採らない条件のため、約定列の完全一致までは実証していない。
- MIXのPBは品質・モメンタムを常時ON相当で実装し、単体の切替inputを持たない。MIXのRSIは単体側のBE/trail/MaxHold/StructureTP等を持たず、MIXのSCAはコメントどおり本番採用機能だけで、RangeMode/Wick/OppTouch/ATR SL等を持たない。このため今回の探索候補をMIXへそのまま設定できるわけではない。
- MIXはライブ時にアーム状態等をGlobalVariableへ永続化する一方、単体EAはプロセス内状態が中心。通常連続稼働では同値でも、再起動直後のシグナルは状態復元差で一致しない可能性がある。
- 結論: **現行のコアシグナルはコード上ほぼ同値。拡張inputと再起動時状態は非同値**。完全保証には同一データ上のシグナルログ突合が必要。

### Family 3: ブローカー間分解

- XM/OANDA MIXのPB・RSI・SCA本番プリセットは、銘柄名マッピングを除き主要値が揃っている。GBPJPY ADX=10、GBPUSD BB period=30も両方へ反映済み。
- 意図的差分としてOANDA Carryは判定D1・執行H1、XMはD1新バー評価。これはブローカー間のエントリー時刻差を作る。
- OANDAのETH枠は「取扱なし・既定OFF」だが、コードは旧MA200単独で、XMのExitMA40/Cooldown5/災害SL45と非同値。有効化する場合は明確なドリフトになる。
- SCAのセッション時刻は両MIXに同じサーバー時刻の数値を入れている。サーバーUTCオフセット/DSTが一致しなければ実時間窓はずれる。`ops/cross_broker_ledger.py`には手動 `--tz-shift-oanda` があるが自動検出はない。
- 結論: **主要FX枠は設定同値、Carryの執行周期・無効ETH・サーバー時刻が分解要因**。

### Family 30: API / 取引日時整合

- Binance fundingはms epochを秒へ、BitfinexはUTC日番号へ変換しており、`[前日開始, 当日開始)`で参照するためコード上の先読みは見当たらない。テスターはCSV固定、ライブAPI失敗時はキャッシュ/CSVへフォールバックし、鮮度不足時は新規評価を保留する。決済はデータ非依存で継続する。
- 日次APIデータはUTC epoch、SCAと運用ログはブローカーのバー/`TimeCurrent()`を基準にする。クロスブローカー台帳側も時差を手動指定する設計で、UTCオフセット/DSTの自動検証はない。運用時はログの既知同時刻イベントで `--tz-shift-oanda` を校正すべき。
- APIのJSON処理は軽量な文字列パーサで、レスポンスschema変更の検知は「件数不足」に依存する。ただし失敗時は新規停止側へ倒れる。
- 結論: **明白な先読み/単位バグはなし。時差校正とAPI schema監視は運用上の残存リスク**。

### Family 31: 限界DD寄与配分

リポジトリ内に利用可能な本番deal/mixlog CSVはなかった。新規収集を行わない条件のため **要データ収集**。`MIX_EA`のDEAL/DAILYログと `ops/cross_broker_ledger.py` の処理基盤は存在するが、限界DDは同時系列の全枠deal/equityが揃わないと算出できない。

# 採用判断と本番反映（2026-08-10・Claude実施）

ユーザーが以下3件の採用を承認したため、本番へ反映した。

## ① PB GBPJPY: EMA組 20/50 → 25/60 → **採用**

本番yaml（採用後）での実測: IS +33,133 / PF3.118 / DD5.93% / 16取引、
OOS +20,763 / PF1.639 / DD14.68% / 26取引。Codexの報告値と完全一致。
全指標で現行以上（IS微増・OOS+41.5%・DD 18.13→14.68%）のトレードオフなし改善。

## ② PB GBPJPY: 構造TP(B10)有効化 → **検証の結果、不採用に差し戻し**

ユーザーは①②③すべて採用を指示したが、①を同時採用した状態で②を実測したところ
**構造TPは一切発火せず、ON/OFFで結果が1円も変わらない**ことが判明した:

| 構成 | IS | OOS |
|---|---:|---:|
| EMA25/60 + 構造TP OFF | +33,133 / PF3.118 / DD5.93% / n16 | +20,763 / PF1.639 / DD14.68% / n26 |
| EMA25/60 + 構造TP ON (LB30/MinRR1.5) | **完全同一** | **完全同一** |
| EMA25/60 + 構造TP ON (LB50/MinRR1.5) | **完全同一** | **完全同一** |
| EMA25/60 + 構造TP ON (LB30/**MinRR0.5**) | +15,833 / PF2.110 / n18 | **+435** / PF1.012 / n37 |

原因: 構造TPは「構造距離が MinRR×SL 以上」かつ「RR由来TP(=4.0×SL)より近い」場合のみ発火する。
MinRR=1.5だと発火窓が 1.5×SL〜4.0×SL と狭く、EMA25/60の少数エントリー（IS16件/OOS26件）では
該当する取引が皆無だった。F9でOOS改善を示したのはEMA20/50時点の別のエントリー集合での話であり、
①を採用した時点でその前提が消滅した。

さらにMinRR=0.5まで下げると発火するようになるが、**IS −52%・OOS −98%と激烈に悪化**する。
つまり「効かない設定」と「有害な設定」の間に安全域がほぼ無い。

**判断: 測定可能な便益がゼロで、隣接パラメータが極めて危険なため、本番では既定OFFに戻した。**
（MIX_EA側の実装自体は温存し、単体EAとの機能パリティを確保。将来の再検証は可能。）
ユーザーの承認判断の前提（OOS改善）が①採用によって失効したための差し戻しであり、
再度有効化したい場合は指示があれば戻せる。
