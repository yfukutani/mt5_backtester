# 第9ラウンド事前査読

結論から言うと、2軸とも実装して測ること自体は妥当です。ただし提示案のままでは、PB は「寿命」を正しく測れず、ライブ再起動時に寿命を延長します。Pair は保有中の更新方針は正しいですが、初期化・再起動時の扱いを決める必要があります。

`backtest.ini` は読んでいません。

## A-1. PB armed 寿命

### 判定

- `amb=0` で売買シグナル・発注結果は現行と同じです。
- ただし提示案は `armedBuyAge` を毎バー更新するため、厳密な「一ビットも変えない」をライブの状態保存まで含めて言うなら不十分です。
- 最大の問題は、押し目条件が連続した場合に毎バー `Age=0` へ戻ることです。このままでは「最初に arm された足から N バー」の寿命になりません。

現行の `armed` は `up/dn` が壊れるか、発注時にしか消えません。[ProcPullback](C:/Users/f/source/repos/mt5_backtester/experts/MIX_EA_SIMVERIFY.mq5:2355)

### 1. `amb=0` の同値性

提示コードは `amb>0` の期限判定以外で `armed` の set/clear 条件を変えていないため、**テスター上の売買結果は同値**です。

ただし次を追加すると、既定値ゼロでもライブの副作用が生じます。

- `armedBuyAge` / `armedSellAge` を永続化スナップショットに足す
- ゼロ時にも毎バー Age を加算する

既定ゼロでの実務上の不変性を強く保つなら、`amb<=0` は現行の set/clear ブロックをそのまま通し、Age を触らない分岐にしてください。対照 run で既存基準と一致させるべきです。

### 2. Age の順序と `amb=1`

提示順序では、条件が単発である限り意図どおりです。

- arm された足: `Age=0`、使用可
- 次の足: `Age=1`、使用可
- その次の足: `Age=2`、`Age > 1` で失効

従って、`amb=1` は「セット足＋次の1足」です。ここで比較を `>=` に変えるとセット後の次足が使えなくなるので、`>` は正しいです。

ただし「新バーごとに必ず1回」は正確ではありません。`ProcPullback()` はバッファ取得失敗で早期 `return` するため、そのバーでは加算されません。一方、外側では既に `lastBar` が更新されるため、そのバーを後から再評価もしません。[新バー制御](C:/Users/f/source/repos/mt5_backtester/experts/MIX_EA_SIMVERIFY.mq5:1538)  
通常のテスターでは問題化しにくいものの、ライブでデータ未準備なら寿命が実バー数より長くなります。

### 3. 本質的な順序バグ：連続押し目で寿命が更新される

この行は毎バー実行されます。

```cpp
if(up && lp<=fastema && qb) {
   S[i].armedBuy=true;
   S[i].armedBuyAge=0;
}
```

したがって `lp<=fastema` が3バー連続すれば、毎回 Age がゼロへ戻ります。期限切れ後も同じ押し目条件が続けば、再 arm します。

これは「最後に押し目条件を満たした足から N バー」にはなりますが、依頼文の「セットされてから N バー以内」とは異なります。第5ラウンドで問題になった「止めた注文が後ろへずれる」構造を PB 側に持ち込みます。

期限を本当に測るなら、少なくとも `pullbackNow` の立ち上がりでだけ arm し、押し目条件が一度消えてから再成立した時だけ新しい arm と見なしてください。`armed` が失効したことを理由に、継続中の同一押し目を再 arm してはいけません。

### 4. ライブ再起動時の永続化漏れ

PB の `armedBuy/Sell` は Global Variable に保存・復元されています。[状態保存](C:/Users/f/source/repos/mt5_backtester/experts/MIX_EA_SIMVERIFY.mq5:1359)

Age を追加しても、次を追加しなければ再起動時に Age はゼロとなり、古い arm が新品扱いになります。

- `SLEEVE` の `armedBuyAge` / `armedSellAge` 初期化
- `StSnap()`
- `StSave()`
- `StRestore()`

ただし毎バー Age を保存する設計は不要な書込みを増やします。より安全なのは「arm されたバー時刻」を保存し、復元時に H4 バー数へ換算する方式です。今回の短期測定だけならテスターでは影響しませんが、本番実装なら未対応で入れてはいけません。

### 5. 第5ラウンドの「ずれ」は当てはまるか

**当てはまります。提示案のままなら強く当てはまります。**

- 期限切れ後も `lp<=fastema` が続けば、次の足で再 arm されます。
- 一度条件が消えて再成立すれば、それは新しい押し目として再 arm されます。
- 後者は設計上妥当ですが、前者は同じシグナルを後ろへずらすだけです。

したがって、今回の PB 試験は「古い押し目を削る」試験にするなら、継続押し目の再 arm を防ぐ必要があります。防がなければ測るのは「arm の最終更新時刻を N バーに制限する」別の軸です。

## A-2. `PairRequireZTurning`

### 判定

保有中も `zPrev` を更新する方針は正しいです。保有中に更新しないと、決済後の判定が数日〜数週間前の Z と比較され、直近の縮小ではないものを「turning」と誤認します。

現行 Pair は flat 時だけ新規建てし、保有時は exit/stop/保有期限のみを処理します。[ProcPair](C:/Users/f/source/repos/mt5_backtester/experts/MIX_EA_SIMVERIFY.mq5:2650)

### 1. 判定式

提示式は、閾値を超えている側では `abs(z)` が縮小していることと同値です。

```cpp
z >= entZ  → z < zPrev
z <= -entZ → z > zPrev
```

これは「乖離の絶対値が縮んだ」という目的に合っています。`zPrev` 自体が反対符号の場合も、誤って通ることはありません。

ただしこれは価格スプレッドそのものの縮小ではなく、ローリング平均・標準偏差の更新を含む **Z の縮小**です。それで測る、と明示しておくべきです。

### 2. 初期化と再起動

追加が必要です。

- `SLEEVE` に `double zPrev; bool zPrevValid;`
- `ZeroSleeve()` で `0.0 / false`
- ライブ再起動後の扱い

`PairRequireZTurning=true` の最初の有効バーは、`zPrevValid=false` なら意図どおり新規を止めます。ただしライブ再起動のたびに最初の1バーを捨てます。

本番品質を保つなら、次のどちらかが必要です。

- `zPrev` と `zPrevValid` を保存・復元する
- 初回に shift=2 の過去バーから前回 Z を再計算して初期化する

また、`CopyClose()` 不足や `sd<=0` の早期 return では更新されません。「毎バー必ず更新」は正しくは「Z を計算できた各評価バーで更新」です。`sd<=0` の場合は `zPrevValid=false` に戻すほうが安全です。

### 3. 第5ラウンドの教訓

**Pair には明確に当てはまります。**

これは「極端な乖離を禁止するフィルタ」ではなく、乖離が反転するまで entry を待つタイミング規則です。

- 今日 `|z|>=entryZ` でも拡大中なら入らない
- 明日も閾値外で Z が縮小すれば入る
- 一気に閾値内へ戻れば、その取引は消える

従って、取引ログから「拡大中の entry は損」と切り取って期待値を見積もるのは無効です。EA 実測では、消える取引と後ろへずれる取引を分けて数える必要があります。SCA 時間帯ゲートで、切り直しが削除を予測した取引の89〜94%が後ろへずれた事実と同型です。[第5ラウンド](C:/Users/f/source/repos/mt5_backtester/docs/oanda_fx_sleeve_quality_round5_20260919.md)

## 実装上の最低条件

- PB は `armMaxBars==0` のとき現行ブロックをそのまま使う。
- PB の arm 起点を「押し目条件の立ち上がり」に定義し、継続中の押し目で Age をリセットしない。
- PB Age を本番利用するなら保存・復元する。
- Pair は `PairRequireZTurning==false` では `zPrev` を更新しない。既定値ゼロの運用副作用を避けられます。
- Pair は true のときのみ、Z を算出できた評価バーで更新する。
- 新 input は負値を拒否し、PB の上書きは USDJPY / GBPJPY の2枠だけに限定する。
- 対照 run は既存 `W000/Z000` と、損益・deal 数・枠別和が一致することを確認する。

# 残った案の棚卸し更新

## 結論

この2軸を、上記の状態機械を正して測り終えた時点で、**「FX 9枠の質改善」として実行価値のある未測定軸はゼロ**です。
