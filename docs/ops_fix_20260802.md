## 1. S-7: watchdog独立ハートビート（完了）

**問題:** A-2（成果物鮮度監視）は `check_and_recover.ps1` の中に同居しているため、
watchdog が死ぬと A-2 も死ぬ。2026-07-31〜08-02 の54時間停止が**誰にも通知されなかった**根本原因。

**成果物:**

| ファイル | 内容 |
|---|---|
| `ops/heartbeat_lib.ps1` | `launcher_log.txt` の実行途絶を外部から検知する関数群 |
| `ops/test_heartbeat_lib.ps1` | **36/36 PASS**（実際の07-31障害のリプレイを含む） |
| `forward_test/watchdog_heartbeat.ps1` | 運用PCローカルのランナー。`heartbeat_log.md` に追記＋msg.exe通知 |
| スケジュールタスク `EA-Watchdog-Heartbeat` | 30分ごと（:20/:50・watchdogの:05/:35とずらす）＋ログオン時 |

**設計上の要点:**

- ギャップは**市場時間との重なり**で重み付けする（`Get-MarketOverlapMinutes`、月06:00〜土06:00 JST）。
  週末の50時間停止は0分、火曜の3時間停止は180分として扱う。実際の07-31障害は
  **54時間00分のうち市場時間1134分（金曜セッションの残り全部）**と算出される
- 同じギャップを何度も通知しないよう `heartbeat_state.json` で報告済みキーを保持。
  ただし**継続中**のギャップは3時間刻みで再通知する
- タスク自体の Disabled / 異常終了も検知する

**実データでの動作確認（2026-08-02 17:36）:**

```
ALERT watchdog gap recovered (54.0 h, 1134 min inside market hours) 2026-07-31 11:05 -> 2026-08-02 17:06
```

**この検証で見つけた自分のバグ2件（修正済み・回帰テスト追加済み）:**

1. `LastTaskResult != 0` を一律「異常」としていたため、**watchdogの実行中に検査が走ると必ず誤報**した
   （実測 267009 = `SCHED_S_TASK_RUNNING`）。0 / 267009 / 267011 / 267012 を良性として許可リスト化。テスト `t-1`
2. 空のコレクションを `[Parameter(Mandatory)]` に渡すと例外になり、
   **「watchdogが一度も走っていない」という最も重要なケースで落ちる**。`[AllowEmptyCollection()]` を追加。テスト `g-8`
3. （精度）市場時間の重なりを1時間刻みの中点サンプリングで求めていたため境界が丸まっていた
   （実障害を1140分と誤算出）。日単位の厳密な区間交差に書き直し、1134分に一致。テスト `r-3`

**既知の限界（正直に）:** 管理者権限が無いため、このタスクも `InteractiveToken` で登録されている。
つまり**誰もログオンしていない間はハートビート自身も眠っている**。
価値は**遡及検知**にある — セッションが復帰した瞬間にギャップが発見・記録・通知される（今回は54時間気づかれなかった）。
真にログオン非依存にするには S-5（§2）が必要。

### 2.0 適用時につまずいた点（記録）

`ops/fix_watchdog_admin.ps1` を**正しいコマンドラインで実行したのに何も適用されない**事象が起きた。
イベントログ（2026-08-02 18:59:23）には期待どおりのコマンドが記録されていた:

```
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ...\fix_watchdog_admin.ps1 -ApplyActiveHours -ApplyWatchdogS4U -Apply
```

原因は**起動元が非昇格のPowerShellだったこと**。`f-pc-N1` は `BUILTIN\Administrators` のメンバーだが、
通常のPowerShellでは UAC によりトークンがフィルタされ `Medium Mandatory Level` かつ Administrators が
`deny only` になる。スクリプトは昇格ガードで停止し何も書き込まずに終了していた。

**問題は、その警告の直後に現在値のダンプが続くため「正常に完了した」ように見えたこと。**
対策としてスクリプトを改修した:

- 非昇格時は**自動で UAC 経由で再起動**する（`-NoExit` 付きなので昇格ウィンドウに結果とチェックリストが残る）
- UAC 拒否時・`-NoSelfElevate` 指定時は **枠付きの `NOTHING WAS CHANGED`** を出す（見逃し不能・終了コード1）

**教訓: 「管理者で実行してください」と書くだけの受け渡しは失敗する。スクリプト自身が昇格するか、
失敗を見逃せない形で表示すること。**

### 2.2 S-6: アクティブ時間（適用済み）

**現状の実測値は `ActiveHoursStart=5` / `ActiveHoursEnd=11`** ＝ Windows は
**取引時間の大半を「再起動してよい時間」として扱っていた**。07-31の再起動が 11:30 に起きたのは、

（NYクローズ後〜東京前）で、18時間上限のもとでは最もマシな6時間。
`SmartActiveHoursState=0` も併せて設定し、Windowsが使用パターンから勝手に窓を再設定するのを止める。

### 2.4 ⚠️ セッション0で復旧が走った場合の副作用（新規・要観察）

S4U化により、**ユーザーがログオンしている最中に復旧が発動した場合の挙動が変わる**。
`Invoke-Recovery` の各段を session 0 の視点で追うと:

| 段 | セッション0からの挙動 |
|---|---|
| `Get-Process terminal64` | 同一ユーザーなので**セッション1のプロセスも見える**（RunLevel=Highestなら確実） |
| `$p.CloseMainWindow()` | クロスセッションでは**効かない**（false を返すだけ） |
| `Stop-Process -Force` | **効く** → ユーザーの画面上の端末が強制終了される |
| `Start-Process $t.ProcessPath` | **セッション0で起動** → ユーザーからは**見えない端末**になる |

つまり最悪ケースでは、**デスクトップから端末が消え、見えないセッション0の端末が代わりに動く**。
取引自体は継続しうるが、ユーザーが「端末が落ちた」と誤認して手動起動すると
**同一データフォルダに二重起動を試みる**ことになり、S-4の二重ロード事故と似た状況を招きうる。

**観察方法:** `launcher_log.txt` に `RECOVERED` が出た直後に、デスクトップ上で3端末が見えているかを確認する。
見えていなければセッション0に移っている。その場合は §2.5 の代替案に切り替えること。

**より良い設計（次の作業候補）:** S4U watchdogは「検知と通知」に徹し、対話セッションが存在するときは
そのセッション側のタスクに復旧を委譲する（オンデマンド起動の `InteractiveToken` タスクを別に用意する）。

### 2.5 うまくいかない場合の代替案

**「watchdogは走ったが端末が戻らない」または §2.4 の副作用が出る場合**は S4U を諦め、
`LogonType=Interactive` に戻したうえで**再起動後に必ずセッションが存在する状態を作る**:

```
$p = New-ScheduledTaskPrincipal -UserId "$env:USERDOMAIN\$env:USERNAME" -LogonType Interactive
Set-ScheduledTask -TaskName "EA-MT5-Watchdog" -Principal $p
```

そのうえで:

- **Windowsの設定 → アカウント → サインイン オプション →
  「更新後にサインイン情報を使ってデバイスのセットアップを自動的に完了する」を ON**

これは**意図的にGUI操作として残してある**。資格情報が必要な操作であり、アシスタントが代行すべきではない。
**レジストリに `AutoAdminLogon` + 平文 `DefaultPassword` を書く方法は採らないこと**（パスワードが平文で残る）。

## 4. 訂正: 旧 F-3 / A-3 の撤回

**改善案の初版は、17:08の3端末EAデタッチを「本ルーチンのMT5 Python読み取りが原因」と断定した。これは誤り。**

端末ジャーナルが示す真の因果（3端末とも同一）:

```
17:07:04  LiveUpdate  new version build 6090 (IDE: 6090, Tester: 6090) is available
17:07:10  LiveUpdate  downloaded successfully
17:08:10  LiveUpdate  start "...\liveupdate\terminal64.exe" /update /path:"..." /config:"..."
17:08:11  Experts     expert MIX_EA_OANDA (USDJPY,M15) removed        <- 更新開始の1.5秒後
17:08:15  Terminal    stopped with 0
17:08:45  Terminal    OANDA MetaTrader 5 x64 build 6090 started
```

**反証（実測）:**

- 17:39、**単一端末**に `initialize(path=)` → `shutdown()` → `removed` は発生せず
- 修正版 `ops/mt5_read.py` で3端末読み取り → `detached_after_read: []`（デタッチ0件）

Python読み取りが同じ分に走っていたのは偶然（54時間停止からwatchdogが17:06に3端末を再起動 →
端末が即座に更新チェック → 17:08に更新実行、という連鎖）。

**教訓:** 時間的に近接しただけの自分の操作を真因と早合点した。
**端末ジャーナルの `LiveUpdate` 行を先に確認すべきだった**（初回のジャーナル読み取り時に
`LiveUpdate downloaded successfully` は視野に入っていたのに結びつけなかった）。
なお同日の週次レポート `2026-08-02_weekly.md` は当初から build 5836→6090 を正しく原因として記載していた。

**`ops/mt5_read.py` は残す** — 前提は誤りだったが、1端末=1サブプロセスの分離はライブ機では妥当な形であり、
`build`/`trade_allowed` 監視という S-8 の用途がある。
