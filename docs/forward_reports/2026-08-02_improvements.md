### 🟠 F-5（設計と実挙動の乖離）リバーサルBoost の判定が |drift|≈0 のときフィード依存のコインフリップになる

- SCA のリバーサルBoost（ロット2倍）は drift の**符号**とブレイク方向の一致/不一致で決まる。drift がゼロ近傍だと符号がブローカー間で反転する
- **07-28 GBPJPY が実例**: drift OANDA **+0.023** / XM **−0.005**。ロング側ブレイクに対し OANDA は「同符号＝Boost無し 0.01lot」、XM は「逆符号＝Boost発動 0.02lot」となり、**同一シグナルで実効ロットが2倍ずれた**（結果 XM −272円 / OANDA −102円）
- 18営業日の GBPJPY で **drift 符号不一致は3件（07-09・07-22・07-28）＝17%**。いずれも |drift| < 0.10 の微小値
- 現行実装は素の符号判定であり、drift の大きさに閾値（デッドバンド）が無い。バックテストは単一フィードで走るため、この不安定性はテスターでは一切顕在化しない

### 🔴 S-5（新規・最優先）watchdog タスクを本当にログオン非依存にし、再起動を生き延びさせる

- **仮説:** `EA-MT5-Watchdog` の `LogonType` が `InteractiveToken` である限り、無人再起動後は watchdog が構造的に走らない。
  実行主体の変更（`S4U` または `Password`）と起動時トリガーの追加により、再起動後30分以内に自動復旧する状態にできる
- **根拠（観測データ）:** F-1。PCは連続稼働していたのに watchdog は 54時間走らず（08-01 は 0 行）、`NumberOfMissedRuns=0` で異常としても記録されない。タスク定義XMLに `InteractiveToken` を実測
- **検証方法（合格条件）:**
  1. 変更前の再現確認 — 手動再起動 → 対話ログオンせずに30分待ち、watchdog が走らないことを確認（**08-02の事象で実証済みのため省略可**）
  2. 変更後 — 手動再起動 → **対話ログオンせずに** 30分以内に `launcher_log.txt` にエントリが出て、3端末がEA付きで復帰することを確認。**3回連続の再起動テストで 3/3**
  3. **副作用の必須確認:** `S4U` はセッション0（非対話セッション）で実行されるため、GUIアプリである `terminal64.exe` の起動が失敗しうる。
     ステップ2で失敗する場合は `S4U` を採らず、**「自動ログオン（AutoAdminLogon）＋ `InteractiveToken` 維持＋起動時トリガー追加」**に切り替えて再度 3/3 を取る
  4. 既存の復旧パス（kill→再起動→ポーリング、実績15/15・平均25秒）は変更しない
- **期待効果:** 今回級（53時間36分・営業日1日分）の停止をゼロにする。これは損益改善ではなく**サンプル収集の欠損を止める**ための投資であり、フォワードテストの目的そのものに直結する

### 🔴 S-6（新規）Windows Update の自動再起動を市場時間外に封じ込める

- **仮説:** 更新の再起動タイミングを制御すれば、S-5 とは独立に停止の**発生確率**そのものを下げられる。S-5（復旧側）と S-6（予防側）は二重防御として併用すべきで、どちらか一方では不十分
- **根拠（観測データ）:** F-1。再起動は 07-31 **11:30 JST**＝金曜の東京セッション中〜ロンドン前という最悪の時間帯に、`MoUsoCoreWorker.exe` と `TrustedInstaller.exe` の2段で発生した
- **検証方法（合格条件）:** アクティブ時間／再起動ポリシー設定後、`Get-WinEvent -FilterHashtable @{LogName='System';Id=1074}` を **4週間**監視し、取引時間帯（月06:00〜土06:00 JST）の計画再起動が **0件**であること。0件でない場合は設定が効いていないと判定して方式を見直す
- **期待効果:** 停止事象の発生頻度を下げる。S-5 が復旧を保証しても、再起動〜復旧までの最大30分の取りこぼしは残るため、予防側の価値は消えない

### 🔴 S-7（新規）監視の単一障害点を解消する — watchdog の外側から watchdog を見る

- **仮説:** A-2 を watchdog 本体から分離し、独立したハートビート（別タスク、あるいは別ホスト／外部通知）にすれば、watchdog 自身の停止を検知できる
- **根拠（観測データ）:** F-2。08-01 の週次レポート欠落も 07-31 の health_log 欠落も、**検知系が同時に死んでいたため 54時間ゼロ通知**だった。07-18 の「安全網の沈黙」（S-2）と同じ構造の再発である
- **検証方法（合格条件）:** `EA-MT5-Watchdog` タスクを意図的に無効化し、定義した猶予時間内（例: 90分）にアラートが上がることを **3/3** で確認。逆に watchdog 正常時に誤アラートが出ないことを1週間確認（誤検知0件）
- **期待効果:** 「安全網が黙っている＝正常」という誤読の解消。今回のような可用性障害の平均検知時間を 54時間 → 数時間オーダーに短縮する

### 🟠 A-3（新規）週次ルーチンの MT5 読み取り手順を非破壊に変える

- **仮説:** `initialize(path=端末exe)` が端末の再起動を伴うことが EA デタッチの原因であり、
  (a) 起動中の端末に `mt5.initialize()`（`path` 引数なし）で接続する、または (b) mixlog と端末側レポート出力のみで代替すれば、EA を落とさずに必要データを取得できる
- **根拠（観測データ）:** F-3。3端末すべてで `removed` → `Terminal stopped` → プロセス再生成が同一パターンで発生し、再起動後はEA未アタッチだった。全期間のジャーナル走査で Python 由来の `removed` は今回が初出
- **検証方法（合格条件）:**
  1. 市場クローズ中に (a) を実行 → ジャーナルに `removed` が出ないこと、かつ取得できる口座履歴が従来手順と**完全一致**すること。**3/3**
  2. (a) が不可（未起動端末に接続できない等）なら (b) に切り替え、mixlog と口座履歴の突合精度が落ちないことを確認
  3. **暫定運用（S-5/A-3の実装前でも即適用可）:** 週次ルーチンの最後に `launcher_log.txt` と3端末ジャーナルを見て **EAが再アタッチされていることを必ず確認し、レポートに1行残す**

### 🔵 B-4（新規）SCA GBPJPY のレンジ境界に対する感度をバックテストで測る

### 🔵 B-5（新規）リバーサルBoost に drift のデッドバンドを入れる

- **仮説:** `|drift| < k × ATR`（または `k × range`）のとき Boost を発動しない（ロット倍率1.0のまま）とすれば、フィード依存のコインフリップを排除できる。
  drift がゼロ近傍の取引はそもそもリバーサル性が弱いはずなので、エッジをほとんど失わずにばらつきだけ減らせる
- **根拠（観測データ）:** F-5。GBPJPY 18営業日で drift 符号不一致 **3件（17%）**、いずれも |drift| < 0.10。
  07-28 は実際に **OANDA 0.01lot / XM 0.02lot** という実効リスク2倍の差になった
- **検証方法（合格条件）:** every_tick・スプレッド実費込みで **k = 0（現行）/ 0.05 / 0.10 / 0.20** を比較。SCA 3枠（GOLD / USDJPY / GBPJPY）を個別に評価する。判定は:
  1. **IS/OOS 両期間プラスを維持**すること（必須ゲート）
  2. k > 0 で月利の劣化が **10%未満**に収まること
  3. 出力に **Boost 発動回数と Boost 起因の損益内訳**を必ず出させ、「Boost が実際に稼いでいるのか」を分離して確認すること（デッドバンドの是非以前に、Boost 自体の寄与が正かを見る）
  1.と2.を満たす最小の k を採用候補とする。満たす k が無ければ現行維持
- **期待効果:** 同一シグナルでブローカー間の実効ロットが2倍ずれる事象の解消。設計どおりのリスク量への収束
