### 🔴 F-1（機能・S級・**週次と評価が異なる**）00:06 JST の端末再起動は「定時再起動」ではなく watchdog の誤検知である

- **週次レビューの記述**: ②口座サマリー注記で「3プロセスとも稼働中（**07-25 00:06 の定時再起動後**）」と、
  正常な定時処理として扱っている。**これは誤り。`check_and_recover.ps1` に定時再起動の機能は存在しない**
  （設計思想は冒頭コメントのとおり「健全な端末には触れない check-first」）。
- **根拠（launcher_log.txt の全数調査）**:
  - `PROBLEM DETECTED` は**全15件**。時刻分布は 07-21 / 07-22 / 07-23 / 07-24 / 07-25 の各日
    **00:05:59・00:06:2x・00:06:5x**（3端末×5日）ちょうど。**それ以外の時間帯の実行（1日46〜48回）は全て `OK - untouched`**。
  - `ESCALATION` は0件。すなわち **watchdog が今週検知した「異常」15件は、100%が誤検知**。
- **根拠（端末エキスパートログ）**: `logs/20260722.log`（OANDA FX）の冒頭が
  `00:05:59.966 expert MIX_EA_OANDA (USDJPY,M15) removed` → `00:06:02.803 exit with code 0` →
  `00:06:10.742 successfully initialized from start config` → `00:06:15.490 loaded successfully`。
  3端末×5日すべてで同一パターン。**健全な端末が強制終了・再起動されている。**
- **原因（コード特定済み）**: `check_and_recover.ps1:47` の `Get-LatestSessionText` が
  **当日の `logs\<yyyyMMdd>.log` のみ**を参照する。日付が変わった直後は当日ログが未生成、
  または `started for` / `loaded successfully` をまだ含まないため、`Test-EaLoaded`（同 :57）が
  **健全な端末に対して必ず false を返す**。00:00 直後に実行が当たると 100% 誤検知する構造。
  watchdog は 00:05:59 に実行されるため、**毎日必ず該当する**。
- **実害**: ①毎日3端末で計約60〜90秒の完全停止 ②**F-2 の引き金**（後述）③F-3 の決済遅延と時間的に一致。
- **副次的に判明した好材料**: kill → 再起動 → ポーリング確認という**復旧パス自体は15回すべて成功**しており、
  平均復旧所要は約25秒。復旧機構の健全性は（意図せず）実証された。**S-1 の格下げ根拠はここにある。**

### 🔴 S-3（新規・最優先）watchdog の EA稼働判定を日跨ぎに耐えるよう修正する

- **仮説**: `Test-EaLoaded` が当日ログのみを参照しているため、日跨ぎ直後は健全な端末でも必ず「EA未ロード」と判定される。
  判定ソースを「プロセス実在＋直近セッションの起動記録」または「ログ更新の鮮度」に変えれば、
  **誤再起動は消え、真の脱落検知能力は落ちない**。
- **根拠（観測データ）**: F-1。`PROBLEM DETECTED` 全15件が 00:05:59〜00:06:50 に集中、
  他の時間帯の実行（1日46〜48回）は全て `OK`、真の脱落は5日間で0件、`ESCALATION` 0件。
  端末ログ側でも `removed` → `exit with code 0` → `loaded successfully` が3端末×5日で再現。
  原因コードは `check_and_recover.ps1:47`（`Get-LatestSessionText` の当日ログ限定参照）。
- **検証方法（採用判断のゲート）**:
  1. **EAではなく運用スクリプトの修正**のため、バックテストゲート（every_tick / IS-OOS）の対象外。
     ただしプロジェクトの規律に従い、**取引環境への変更はユーザー判断**とし、本レポートは提案までとする。
  2. 修正候補（いずれか、または併用）:
     - (a) 当日ログが無い／`started for` を含まない場合は**前日ログの末尾セッション**も参照する
     - (b) 判定を「`terminal64.exe` が存在し、かつ **mixlog または端末ログが直近N分以内に更新**されている」に変更
     - (c) 保険として **00:00〜00:15 JST の実行はスキップ**する時間帯ガード
  3. **採用判定基準**: 修正投入後 **7日間で `PROBLEM DETECTED` が0件**、かつ
     意図的に1端末のEAを外す検証（ユーザー実施・任意）で **30分以内に検知・復旧**すること。
     この2条件を**両方**満たすこと（片方だけでは「検知しないだけ」の劣化と区別できない）。
  4. 併せて **F-3 の因果を確定**させる: 修正後の最初の PairTrade 決済が XM と同一秒に執行されれば F-1 起因と確定。
     依然ずれるなら、EA の決済判定タイミング（H1足確定 vs OnInit 再評価）の課題として別項目に切り出す。
- **期待効果**: 毎日の無用な全端末停止（3端末×約25秒×日次）の解消。
  シグナル時間帯（SCA: JST 15:15〜17:00 / PairTrade決済: JST 00:00 / RSI・VBO: JST 18:01）と再起動窓の衝突リスク排除。
  **警報の信号対雑音比を 0/15 から回復させ、S-4 の再発経路を断つ**。

- **根拠（観測データ）**: F-2 および週次レビュー 🚨A。
  - 07-20 は EURUSD,H1 単独 → **07-21 00:07 の誤再起動以降 2インスタンス**（端末ログで確定）。

  1. **端末構成の是正（ユーザー実施・EA変更不要）**: XM端末で**両方のチャートからEAを外し**、
     `MIX_EA_Ftest_XM_v13.set` を明示指定して**1枚だけ張り直す**
