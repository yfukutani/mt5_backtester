## 1. 前回の結論のどこが間違っていたか

`oanda_fx_scagj_weight_20260915.md` §4 は、正しい発見をして、そこで止まっていた。

> **このブックの制約は、DDでもリスク許容度でもなく「レバレッジ25の証拠金」だった。**
> Claude案 **A10（証拠金維持率でロットを制限する）**が、
> 制約として最後まで残った唯一の軸である。

ここで **A10 を「制約」として扱ったのが誤りだった。**
「証拠金が 215% だから T039 は実行できない」——そう判定して構成を捨てた。

**だが 215% は「ピーク」であって「常時」ではない。**
T039 の OOS で使用証拠金が equity の 100% を超えたのは **2,750時点中 76時点（2.8%）**である。
**残り 97.2% の時間は、その構成は何の問題もなく動いていた。**

> [!important] **A10 は制約ではなくサイジング規則である。**
> 「収まらないから構成ごと捨てる」のではなく、「**収まる分だけ建てる**」。
> ピークの 2.8% だけロットを削れば、残り 97.2% の成績はそのまま残る。
> **捨てていたのは構成ではなく、構成の 97% だった。**

## 2. どう測ったか — MT5 を1回も回さずに厳密に測れる部分

`ml/fxmargin2/margin_cap_sim.py`

ロットを k 倍に削っても**建玉の値動きは変わらない**。約定価格も決済価格も同じである。
したがって **その建玉の損益はちょうど k 倍**になる。これは近似ではなく厳密である。

厳密でないのは1点だけ——**削った結果 equity が変わると、その後のロットも変わる。**
複利枠のロットは equity に比例する（EAの `LotRisk()` の定義そのもの）ので、
`sim_lot = logged_lot × (sim_equity / logged_equity)` で追従させた。

**自己検証**: cap を掛けずに走らせると、logged の純益を再現しなければならない。

**再現する。** 差は丸め由来である。

## 4. 実行可能性 — 含み損の上界で「証拠金判定の穴」を塞いだ

`ml/fxmargin2/stopout_bound.py`

これまでの証拠金判定には、ずっと同じ警告が付いていた。

> equity は確定損益だけで作っており、含み益・含み損を含まない。

この穴があるままでは A10 の結果を採否に使えない。**近似ではなく上界で塞いだ。**

建玉には SL が入っている。**SL より下へは（ギャップを除き）損は進まない。**
したがってある時点で起こりうる最悪の equity は

```
equity_worst = 確定equity − Σ_建玉 (約定価格とSLの差 × ロット × 契約 × JPY換算)
```

であり、これは**実際に起きうる最悪値の下限**である。
OANDA証券MT5 は**維持率100%で追証・50%でロスカット**なので、
`equity_worst / 使用証拠金` がこの線を割らなければ**ロスカットされない**と言える。

> 「**安全**」は**保証**である（SLが機能する限り、その構成はロスカットされない）。
> 「**★ロスカット**」は**警告にすぎない**——「全建玉が同時にSLまで逆行したら」の話であり、
> 実際にそうなったという意味ではない。**保証の側だけを採否に使う。**

## 5. 見込みの評価 — どこが弱いか、はっきり書く

**この結果でいちばん疑うべきは「cap を掛けたほうが純益が増える」という点である。**
OOS の cap無し 6,431,404円 に対し cap80% は 7,229,106円——**削ったのに 12% 増えている。**

機構としては説明がつく。**ロットを削ると、負けが続く局面で equity の目減りが小さくなり、
その後の複利の土台が高く残る**（ボラティリティ・ドラッグの低減）。
だがこれは**経路依存**であり、**別の期間で同じ符号になる保証はない。**

弱いところを列挙する。

| 懸念 | 度合い | なぜそう言えるか |
|---|---|---|
| **MT5未確認** | **大** | 段階2のみ。EAの再コンパイルが掃引待ちで、まだ1本も回していない |
| **比例近似の外挿** | **中** | cap80%・OOS で 483/1375（35%）の注文を削っており、equity 経路が logged から大きく離れる |
| **最大DD 56.1%** | **大** | 月利6%を狙う代償。T043 の 29.5% の約2倍 |
| **中央値が下がる** | 中 | OOS中央値 1.51%（T043）→ 0.80%（T036 cap80%）。**典型的な月は T043 のほうが良い** |
| ギャップ・スワップ未考慮 | 中 | 上界はSLが機能する前提。週明けギャップはSLを越える |
| SL無し建玉 | 小 | Carry など最大3本・OOSで最大 1,293,504円ぶん。損失に下限が無い |
| cap の選択 | **小** | 70〜85% の台地であり、両窓で一致（§3） |

> [!warning] **「月利5.01%」を成果として扱ってはいけない段階である。**
> 現時点で言えるのは「**MT5で確認する価値が確実にある**」までである。
> 前回まで「6%は届かない」と結論していたので、そこは撤回するが、
> **到達したとは書かない。**

## 6. EA への実装（済・未コンパイル）

`experts/MIX_EA_SIMVERIFY.mq5` に `MarginCapPct` を追加した。**まだコンパイルしていない。**

```mql5
input double MarginCapPct = 0;   // 使用証拠金/equityの上限%（0=無効・段階2の推奨80）

double MarginCapLot(const string sym, const double lot)
{
   if(MarginCapPct<=0.0 || lot<=0.0) return lot;
   double eq=AccountInfoDouble(ACCOUNT_EQUITY);
   if(eq<=0.0) return 0.0;
   double avail=eq*MarginCapPct/100.0 - AccountInfoDouble(ACCOUNT_MARGIN);
   if(avail<=0.0) return 0.0;
   ...  // OrderCalcMargin で1ロットあたりの必要証拠金を出し、avail/m1 で頭打ちにする
}
```

実装で気をつけた点を3つ残す。

1. **`Clamp()` が最小ロットへ「切り上げて」いた。**
   既存の `Clamp()` は `MathMax(mn, ...)` で、どれだけ小さいロットも最小値に戻していた。
   **cap で削った結果が最小未満になったとき、ここで戻すと cap を突き破る。**
   cap が効いた場合のみ 0 を返し、呼び側に捨てさせるようにした。
   （これは `e869324`「risk%が低すぎてロットが最小値に丸め戻されていた」と同じ罠である。）

2. **発注サイトに 0 ロットの番人がいなかった。**
   `LotRisk()` を使う枠（PB・RSI）は `if(lot>0.0)` で守られていたが、
   **SCA・Carry・Pair・VBO・暗号の5経路は `trade.Buy(Clamp(...))` を直に呼んでいた。**
   全経路にガードを入れた。

3. **Pair は片脚だけ出してはいけない。**
   2脚のどちらかが cap で 0 になったら**両脚とも出さない**。
   片脚だけ建てると、中立枠が方向性リスクの枠に変わってしまう。

**EA は段階2のシミュレーションより厳しく・正しい**——`ACCOUNT_EQUITY` は**含み損益込み**なので、
含み損を抱えている最中は cap がより強く効く。
**したがって MT5 の結果は段階2より悪く出る可能性が高い。**
